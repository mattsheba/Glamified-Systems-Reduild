Glamified Systems · Build Process

Glamified Rebuild Playbook

Turning a tech site you admire into glamifiedsystems.com — and then into the reusable engine behind the industry template catalogue. Six phases, run in order.

You picked "a live company site I admire" and "match whatever the source uses." Take the first at face value and adjust the second, for one practical reason before any legal one: a modern production site ships nothing worth copying. What you'd pull down is minified bundles, hashed class names like .css-1x7kzq, compiled Tailwind with every unused utility stripped, and a framework hydration payload that expects a build pipeline you don't have. Rebranding that is harder than building clean, and you'd own a codebase you can't modify a year from now.

So the method is: read the stack, extract the design decisions, rebuild in that same stack. You still get their layout and feel. You get a codebase you can actually run twenty industries through.

01

Draw the line before you start

Goal · Know what's yours to take

This matters more for you than for most people asking this question, because these builds get resold. A site you customise for a lodge in Livingstone at K3,500 is a commercial product, and the tier that ships source files puts the code in someone else's hands.

Yours to take

  • Section sequence and page structure
  • Grid, column counts, spacing rhythm
  • Type scale ratio and hierarchy logic
  • Navigation and IA patterns
  • Interaction patterns — sticky headers, reveal-on-scroll, accordion FAQs
  • How they solve a problem you also have

Not yours

  • Their source code, verbatim or lightly edited
  • Every image, illustration, icon set and video
  • All body copy, headlines and taglines
  • Logo, wordmark, brand name
  • Their exact brand palette, where it is the brand
  • Licensed fonts served from their CDN
Where people get caught

Not the layout — the assets. A hero photograph or an icon set carried across is the thing that generates a takedown, because it's provable in seconds by reverse image search. Strip every asset at extraction time, not at review time.

02

Read the stack and the design system

Goal · Facts on paper, before any code

Don't reach for a scraping plugin here. design-mirror is not installed — that was an assumption in an earlier draft of this playbook, and it cost a turn to discover. You don't need it either. What you want is the rendered design system, and only a real browser can tell you that: Elementor, Webflow and Framer sites declare almost nothing useful in their stylesheets, so the system lives in what the page finally paints. Drive Chrome and read computed styles.

# In Claude Code, pointed at your empty project
claude "open https://the-site-you-like.com in Chrome and read the
  design system off the rendered page — computed styles aggregated
  by frequency: type scale, spacing histogram, colour roles weighted
  by painted area, container max-width, section padding, breakpoints.
  Write design-tokens.md. No assets, no copy."

Frequency is the whole trick. A production page carries hundreds of one-off values; the scale is whatever repeats. Counting nodes per font-size is what separates a real step in the ramp from a widget somebody nudged once — and it is the only way to tell a design system from an accident on a site that has no token layer.

Read two sites, not one

Pick a second reference closer to your own size and market, and extract both. The site you admire is usually built for a scale you are not at — the first run of this phase found an 80px hero and fifteen sections on the aspirational reference, against a 45px hero on a local peer doing the same job. Without the second reading, nothing tells you which one is the anomaly, and you inherit an altitude your content cannot fill.

Then confirm the stack yourself rather than trusting a guess. What the response headers and HTML source tell you:

SignalMeans
Next.js/_next/static/ paths, __NEXT_DATA__ script, x-powered-by
Astroastro- prefixed classes, almost no client JS
TailwindLong utility strings in markup — flex items-center gap-4
WordPress/wp-content/, /wp-json/ reachable
Webflow.w-container, data-wf-page
Framerframerusercontent.com asset URLs
Reality check

If it's Webflow or Framer, there's no stack to match — those are hosted builders that emit machine-generated markup. Rebuild it in Astro or Next and you'll get a faster, cheaper, more maintainable site than the original. Same for a heavily-plugged WordPress site.

What you should have written down before Phase 3

  • Type scale — the actual steps, the ratio between them, and where you cap it. The cap is a decision, not a measurement.
  • Spacing scale — measure the base rather than assuming 4 or 8; it is not always either. Then decide separately whether to inherit theirs or normalise to yours.
  • Color roles — ground, surface, ink, muted, one accent, semantic states. Roles, not their hex values.
  • Container max-width and gutter
  • Section inventory in order: hero → proof → services → … — and the count you are actually going to build
  • Breakpoints, and what collapses at each
  • Any single component worth lifting wholesale — a form, a pricing table, a nav pattern

Write it as decisions with sources attached, not as a list of observations. "Cap the ramp at 56 — reference A used 80, reference B used 45, 80 needs page depth we don't have" is a spec Phase 3 can build against. A table of everything both sites do is just a second thing to read.

03

Write the spec before the code

Goal · A contract the generated code answers to

This is the phase most people skip, and it's the one that decides whether you have a website or an engine at the end. You just installed spec-driven-workflow for exactly this — it produces a spec artifact that tests get derived from, so generated code stays traceable to a requirement instead of drifting.

claude "use spec-driven-workflow. Write the spec for the
  Glamified Systems site from the design system in
  design-tokens.md. Sections, breakpoints, content model,
  acceptance criteria per section."

Force one thing into that spec now, while it costs nothing: every piece of text and every image path comes from a config file, never from the markup. That single constraint is the difference between a site and the Glamified Website Engine. Get it wrong here and industry number four is a copy-paste job again.

// site.config.js — the whole engine idea, in one file
export default {
  brand: { name: "Glamified Systems", tagline: "...", accent: "#0F6E5C" },
  contact: {
    phone: "+260 977 669 883",
    whatsapp: "+260977669883",
    city: "Lusaka, Zambia",
    hours: "Mon–Fri, 08:00–17:00 CAT"
  },
  sections: ["hero", "products", "services", "proof", "contact"],
  products: [ /* GlamifiedHR, Fleet, Sales */ ],
  services: [ /* web + software, IT support, consultancy, ... */ ]
}
04

Build the shell

Goal · Real structure, placeholder content

Build from the spec, in the stack you identified, with your own frontend-design and uiux skills carrying the execution. Structure first — every section in place, responsive, keyboard-navigable — with obviously fake content in the slots. Fake content that looks fake is a feature here: it stops you shipping Lorem ipsum to a client, which happens more often than anyone admits.

Then run the two checks that are cheap now and expensive later:

claude "run a11y-audit on this project"
# WCAG 2.2 — contrast, focus order, labels, landmarks.
# Fix before content, or you fix it in 40 places after.

claude "run env-secrets-manager on this project"

# reaches a public GitHub repo.
For the catalogue

An accessible base template is a selling point you can name in the premium tier, and it's genuinely rare in the Zambian market. It costs you one afternoon once, then ships free with every industry variant.

05

Swap in Glamified's own substance

Goal · The site becomes yours, not a reskin

This is where a rebuild stops looking like the site it came from. Layout can rhyme with theirs; the substance has to be entirely yours — and yours is genuinely different, because you're selling both products and services to a market they don't serve.

Your memory of the last positioning pass says the new homepage leads with products, not services. That decision changes the hero, so honour it here:

SlotGlamified's real content
HeroThe product suite — GlamifiedHR, Glamified Fleet, Glamified Sales
ServicesWeb & software development, IT support, business consultancy, payroll outsourcing, graphic design
ProofNamed Zambian deployments, screenshots of real dashboards, client logos you have permission to use
ContactLusaka · +260 977 669 883 · WhatsApp · Mon–Fri 08:00–17:00 CAT
LegalPrivacy policy, terms, refund policy — flagged as missing in your last site audit

Two things worth building in while you're in here, both from your zambia-local skill: a WhatsApp deep link rather than a contact form as the primary CTA, since that's how enquiries actually arrive; and a hard performance budget, because a hero video that's fine on fibre is a bounced visitor on mobile data.

Last check before Phase 6

Open your build and the original side by side. If a stranger could name the source site from looking at yours, you've matched too closely — usually it's a distinctive hero illustration or a signature color doing it. Change that one thing.

06

Ship it, then fork it into the engine

Goal · One site live, twenty ready

Deploy to Netlify from GitHub as you normally would — and use ci-cd-pipeline-builder to generate the pipeline once, since every industry variant will reuse it.

claude "use ci-cd-pipeline-builder — detect the stack and
  generate a Netlify deploy pipeline with build + a11y check"

Then the fork that makes this a product rather than a job:

  • Glamified Systems site live on its own domain
  • Repo tagged v1-base — the untouched engine base
  • site.config.js holds 100% of brand, copy and contact — nothing hardcoded in markup
  • One industry proven end-to-end by config alone (pick lodges or construction — highest demand, clearest content model)
  • Deploy preview per industry on a subdomain, per your catalogue plan
  • Legal pages written once, parameterised by client name

When that checklist is clean, a new industry demo is a config file and a set of images. That's the K1,500 tier turning a profit instead of eating a weekend.

The short version: read their stack, extract their design decisions, rebuild clean in the same stack, put every word in a config file. You get the site you admired and an engine underneath it — and nothing in the repo that belongs to anyone else.
